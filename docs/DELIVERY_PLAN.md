# Delivery Plan

Authority: [Charter](PROJECT_CHARTER.md), [ADRs](ARCHITECTURE_DECISIONS.md), technical contracts. [Project status](PROJECT_STATUS.md) is the unique progress authority; status cells here are its synchronized projection. Status definitions and completion rules are in [Workflow](WORKFLOW.md). No task ID is reused. Dependencies mean **COMPLETED**, not merely code present. All tasks use local computation and synthetic/publicly distributable fixtures without login.

## Execution rules

Select the first incomplete task in numeric phase/task order whose dependencies are COMPLETED. Mark READY, state acceptance before edits, then IN_PROGRESS. A failed prerequisite blocks downstream readiness; do not skip it. Existing code may satisfy part of a task, but only recorded acceptance evidence closes it. Split oversized tasks into child IDs such as P1-02.01 with their own gates before implementation; the parent retains its original gate and is completed only after its children. Add child rows to both plan and status, explicitly avoiding parent/child dependency cycles. No estimates or percentages imply delivered capability.

Every row requires code or the specified document, positive and negative tests, applicable four Rust checks, contract updates, status/handoff updates and a recorded commit. Phase gates additionally require all phase tasks closed. A stage is not completed by its design. The order is P1 → P2 → P3 → P4 → P5 → P6; Python → Java → Go within P5.

Governance initialization is GOV-01: audited baseline, eight governance documents, linked README/legacy roadmap, repository recovery instructions, document checks, required Rust checks and GitHub main push. Dependencies: existing foundation. Deliverables: this governance set and [Baseline audit](BASELINE_AUDIT.md). Acceptance: internally consistent authority, 40 actionable stage tasks, independently usable handoff, preserved implementation/license/history, confirmed normal push. Test requirements: [Workflow](WORKFLOW.md) checks and remote SHA comparison. Status: VERIFIED pending recorded delivery/closure commit and push.

## Gate evidence and changes

For each completed task record in PROJECT_STATUS: artifact paths, acceptance outcome, test command/count/platform/date, code/evidence commit, unresolved limitations and next task. Large evidence packs may live in dedicated reports linked there; they do not replace the unique progress ledger. Stage-gate reports must reference individual task evidence. A missing external runtime or OS test is a real blocker, not permission to mark a gate complete.

The old phase numbering is retired; its intent is mapped in [Roadmap](ROADMAP.md). New scope must preserve these boundaries and be approved as a scoped task; dates, marketplace operation and a remote trading deployment are not implied by the plan.
