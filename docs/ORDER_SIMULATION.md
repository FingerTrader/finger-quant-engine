# Explicit simulated orders and next-open fills

Implemented experimental P3-03 native Rust library. [Project status](PROJECT_STATUS.md) owns closure; [Simulation](SIMULATION.md) and [Backtesting](BACKTESTING.md) retain full pipeline targets. `fqe_runtime::simulator::SimulationBroker` owns simulation order/fill state while [VirtualLedger](LEDGER.md) remains the only cash/position truth. No SDK, live routing, authentication, network or Flutter dependency exists.

## Versioned executable model

The original model `fqe.next-open-prior-volume/1` accepts only the gross-basis cash-long account profile. Short/margin/borrow, other order types, intrabar touch matching, signed-price fills, tax and live data timing are unsupported. SimulationConfig freezes account/instrument, fixed continuous timeframe, participation/fee/slippage basis points, minimum fee, optional exact strategy run/execution source and explicit bounded limits. A different matching/cost policy requires a new version rather than silently changing this model. This is not Desk cash-market/cash-limit equivalence. The separately versioned [margin-long extension](MARGIN_PROFILES.md) adds authoritative principal/risk/liquidation while retaining these matching conventions.

Observe at least one validated closed bar before submitting any order. Decisions occur after that bar close; only a later source bar can execute them at its open. Equal nanosecond boundaries follow the logical phase: previous close/decision commands, then next open matching. The API consumes already closed bars, so simulated open-time receipts become available only when that complete bar is delivered. No commands can be inserted inside a bar and no wall-clock/realtime fidelity is claimed.

Current bar instrument/timeframe/scales/OHLC/tick/volume range and continuous increasing source ordering are validated. Matching reads its open only. Liquidity is frozen from the previous closed bar's base volume times participation_bps/10000, floored to the quantity step. It never reads the incoming bar's future volume/high/low/close to select its open fills. At most one execution per order per bar consumes a shared FIFO budget in acceptance-number order, independent of textual order ID. No fill occurs with zero budget. This previous-volume convention is an explicit deterministic synthetic model, not a promise of available real market liquidity.

Market orders use next open with adverse slippage. Open-only limit buys execute only if raw open<=limit; sells only if raw open>=limit. Slippage remains capped by the limit and can preserve opening price improvement. A low/high intrabar touch alone does not execute a limit. Orders remain live until filled, cancelled, replaced, rejected, or explicit Finish. No market price/time/venue priority or order-book reconstruction is inferred.

## Intent, admission and provenance

OrderIntent declares a fresh valid ID, buy/sell side, Market/Limit, positive minimum/lot-valid quantity, and explicit origin. Buy requires a positive money-step cash cap; sell must omit it and reserve current long inventory. Order-reference price is current known close or declared limit. Minimum order notional is checked exactly at that reference, without future price information. Fill partials may be smaller than order quantity/notional minima but always respect actual lot steps. Zero money-step gross fills are rejected. All prices/fees/account values stay within the financial contract bounds.

LongBuyPolicy is an optional fixed-quantity/cash-cap mapping. `intent_from_long` validates a matched non-warmup EventObservation, configured run/execution identity, current source bar/close, signal index/instrument/Long kind, then returns an intent only. It changes no hold/order/fill. The host must explicitly submit. Accepted or financially rejected submitted signal origins are consumed once; another order ID cannot reuse that signal. Manual intents remain explicit. These native host DTOs carry provenance and are not cryptographic proof or a hostile-client authorization system.

Malformed IDs/units/ticks/lots/minima/source/duplicates are command errors and leave all state unchanged. A structurally valid submission with insufficient cash/inventory, too-small cap or unsupported reference quote produces an explicit terminal Rejected order receipt with no hold or fill. The rejected order/signal ID stays consumed. At submit, buy cap must cover the estimated full-order slipped reference gross+fee and available cash; sell requires unreserved long quantity. Market gaps can still exceed the cap and reject execution later.

## Costs and accounting

Adverse slippage is raw_price×(10000±slippage_bps)/10000, rounded upward for buys/downward for sells to the actual price tick. Limit clamping then applies. Participation and fee_bps are0..10000; slippage_bps is0..9999. Gross is exact price×fill quantity settled HalfAwayFromZero to the actual money step. Fee is max(minimum_fee, settled_gross×fee_bps/10000), half-away to the money step. This model deliberately computes rate on settled gross; it is not the inspected Desk exact-gross fee formula. Fees apply separately to each partial execution.

The broker reserves buy cap or sell quantity through named VirtualLedger holds. A successful fill consumes only its actual cash/quantity from its own reservation, posts exactly one ledger Trade and records that journal sequence. Full fills release leftover cap. A partial whose remaining budget cannot cover a later execution is terminally rejected with its prior filled quantity retained and remaining hold released; other orders' funds remain protected. Cap cannot silently borrow extra free cash. Price/range/account-limit rejection similarly releases only that order's hold. There is no implicit loan, rounding adjustment balance or client-owned second ledger.

A hand-calculated cost test buys2 at raw100 with1% slippage:price101/gross202/25bps fee0.51/cash797.49; sells2 at raw110:price108.90/gross217.80/fee0.54/final1014.75. Gross realized15.80 minus fees1.05 gives14.75 net. Additional tests exercise actual0.05 ticks, per-fill minimum fee exhaustion, shared fractional liquidity, below-minimum partial lots, price-range and cap gaps, and independent cash/quantity/basis values.

## Lifecycle, atomic commands and limits

Accepted→PartiallyFilled→Filled is the ordinary fill path. Live orders may become Cancelled, Replaced or Rejected; a rejected remainder can have nonzero historical filled quantity. Cancel applies before the next open only if its command precedes that bar input; a cancel after a terminal fill is an error. Replace stages old hold release and new admission together with a fresh ID, resets eligibility to the current closed-bar frontier, and preserves the original unchanged if replacement validation/admission fails. Finish cancels/releases all live remainders and is terminal. Cancel/replace races are deterministic command ordering, not asynchronous exchange behavior.

Every command clones a bounded candidate and commits ledger/order/fill/signal/bar/receipt changes together. A late multi-order failure, including fill quota after an earlier staged fill, discards the complete candidate; the same source bar remains retryable. Individual financial order rejection is a successful explicit outcome and does not fail unrelated orders. Configurable positive order/fill capacities cannot exceed128/2048; command capacity2..2048. One final command slot is reserved for Finish so capacity cannot strand holds. Full receipt/journal history is bounded; no production-scale throughput claim is made.

SimulationReceipt records command sequence, initial full model/config/engine pins, exact command, order/fill transitions and ledger account view. `replay` creates an independent broker, recomputes all commands and compares complete receipts. Every tested split reproduces exact continuation orders/fills and underlying ledger journal. These native Rust DTOs provide no stable wire/ABI, durable append, financial crash-file restore or migration. P3-07/P4 own complete persisted financial run compatibility/output acknowledgement.

## Executed examples and verification boundary

`cargo run --locked --offline -p fqe-runtime --example simulated_orders` loads the actual compiled MACD/RSI model and a six-bar public historical CSV/spec, freezes PreparedHistoricalRun inputs and evaluates locally. Bar5 Long is explicitly converted/submitted, bar6 open fills2 at3.00 with0.50 fee; initial100 becomes cash93.50/position2/zero remaining hold. Finish/recompute replay match. The position remains open; this example is not a full portfolio performance report or liquidation model. Dataset and selection identities are printed.

`order_simulation` tests cover exact hand costs, loaded strategy/source/warmup/index/duplicates/no implicit action, next-open/same-bar/future-HLC/volume traps, FIFO/step liquidity, both open-only limit sides, partials/caps, cancel/replace, invalid bar/gap/minima/units, terminal cleanup, low configured capacities/late whole-bar rollback, every-command replay and tampered model/engine/sequence/account receipts. Original ledger Fraction oracle and full P1/P2 regression remain required. No dependencies/manifest/lockfile/toolchain changes, installers, private scanner uploads or Desk writes/packages/app execution occur. Other broker models, report/orchestration/optimizer, portable transport, installed Desk/Flutter and language/plugin acceptance remain later work.
