# Temporal Windows and Instance Scheduling

Status: experimental P2-03 library profile. This contract owns `fqe.temporal-rules/1`, bounded host windows/timers and workflow-lane coordination. [Market scheduler](MARKET_SCHEDULER.md) retains authority for fixed-UTC domains, inclusive watermarks and market order; [workflow execution](WORKFLOW_EXECUTION.md) owns numeric/rule computation and per-event transactions. No wall-clock dependency or extra financial evaluator is introduced.

## Typed temporal artifact

`fqe_ir::temporal::LoadedTemporalRules::from_bytes` strictly accepts root fields `format:fqe.temporal-rules`, integer `schema_version:1`, bounded identifier `id`, `version`, exact `requirements:["temporal.windows/1"]` and `windows`. Shared bounded JSON decoding rejects duplicate keys, unknown fields/versions/capabilities, floats/unsafe numeric encodings and source/depth/item limits. There are0..16 windows, sorted by unique ID.

Each window declares exactly `{id,arm,predicate,span}`. Arm and predicate reuse workflow sources `{event:root}` or `{instance:id,output:name}`; `bind(compiled_workflow)` verifies both reference exact Boolean public outputs. Count spans are `{kind:closed-bar-count,bars:"3"}`, with count1..1000000 and a required closed-bar workflow trigger. Event-time spans are `{kind:event-time,duration_ns:"30"}`, with positive exact u64 duration. Tick-count, wall-clock, session/month/holiday calendars and undeclared source references fail. Fixed UTC market/calendar validation remains in the underlying schedule.

Canonical bytes normalize window declaration order; artifact/source identities bind canonical/exact source bytes. Bound execution identity combines the temporal artifact with the exact compiled workflow execution ID. A coordinator rejects a temporal binding from a different workflow even when port names agree. No binding executes providers. The schema contains no language object, callback source, financial indicator name or installer. Empty rules and no rules are distinct manifest choices but both create no timers.

## Window semantics

One active window per declared rule belongs to one workflow lane. At each successfully accepted matching workflow event:

- An inactive window arms only when arm is Ready true and the workflow is outside warmup. Record the current global logical source sequence and event time. The arming event contributes no predicate sample and no count: the interval is open on the left.
- An active window evaluates the current predicate; only Ready true outside warmup latches satisfied. Missing/Warmup do not fabricate false typed data or a hit. Once latched, true persists until expiry/cancel/finalization.
- Closed-bar windows count each later admitted matching closed bar once, including the expiry bar. Unrelated streams/ticks, rejected inputs and missing calendar intervals do not count. The nth bar emits one WindowNotice after including that bar's predicate and removes the window. Active re-arms are ignored, including a re-cross on that expiry bar; it cannot reopen until a later event.
- Event-time windows compute `deadline = opened_time + duration` with checked u64 arithmetic. Predicate events at or before the deadline can latch; a later event cannot pass an undispatched deadline. The deadline fires only after the market watermark promises that timestamp complete and all active work at that timestamp has been processed. No market event at the exact deadline is required. Emit one WindowNotice at the exact deadline and remove the window. A re-arm at that deadline is ignored before timer expiry.

The right boundary is inclusive. Notice records window ID, opening logical sequence/time, expiry time, satisfied and cause (closed-bar logical sequence or watermark). The containing dispatch outcome identifies the lane/run manifest. A notice is a temporal observation, not an order/fill or an automatic rewrite of the workflow's own signal rules. The full G-006 MACD/RSI model chooses its decision outputs at P2-06; this generic profile proves the count/latch/boundary mechanics without hardcoding MACD/RSI into scheduling.

Temporal memory is a deep-owned bounded map of typed fields, not persisted state. A late checked-deadline/count error discards the candidate workflow provider/crossing/cell/Delay/cursor updates and temporal changes together. The private workflow candidate-step path reuses the existing evaluator and atomic event staging; it does not introduce another arithmetic implementation or provider update.

## Coordinator, capacity and identity

`instances::InstanceScheduler` owns an initially empty MarketScheduler and1..64 permitted workflow lanes. Limits explicitly specify instance capacity1..64, total pending deliveries1..4096 and per-instance pending1..total. Each declared window permits at most one timer, so64 lanes ×16 windows bounds active windows/timers at1024 without an unbounded heap. No background thread or unbounded internal drain loop exists; `drive_one` performs one bounded quantum.

Attach all lanes before ingress/publication. Each lane has a unique ID/run ID, fixed stream subscription, matching exact trigger and stream dataset ID, immutable shared CompiledWorkflow and optional BoundTemporalRules. Fresh WorkflowRuntime factories/state/crossings, temporal map and FIFO belong to that lane; shared definitions/immutable queued delivery/alignment are Arc-shared only. Source identities are declared provenance, not authenticated dataset IO. `LaneManifest` records host run, lane/stream, schedule identity, complete workflow manifest and optional temporal artifact/source/execution identities. Limits and manifests are readable for recording; they are not restorable snapshots.

Market publication atomically fans out one immutable delivery to all Active or Blocked subscribed lanes. Capacity for every recipient is checked before any queue or market publication changes. Fanout failure returns instance_backpressure with the market record still pending and no partial recipient enqueue. Stopped/Completed lanes receive no future deliveries. A blocked lane continues to reserve bounded queue space; slow/blocked lanes can therefore backpressure upstream. The caller must drain/retry/cancel or rebuild sufficient capacity; no silent drop/eviction or bypass of watermarks occurs. A capacity smaller than a fanout can require explicit cancellation/reconfiguration.

`drive_one` chooses the earliest ready event-time task. At equal time:

1. Existing lane market deliveries run before publishing another market record at that time. This preserves per-event alignment and prevents accumulating an entire timestamp's fanout before draining it.
2. New eligible market records publish in the market scheduler's existing total order.
3. Watermark-eligible timers run after those market records and active same-time lane deliveries.

Within the earliest timestamp/phase, lexical lane order with a retained round-robin cursor chooses the next eligible lane; no active same-phase lane repeatedly jumps ahead. Per-lane FIFO preserves global logical source order even when there are gaps from other streams. Window-ID lexical order breaks equal-deadline timer ties within a lane. Work in a lane before its own deadline blocks that lane's timer. A fixed input/watermark/control-command sequence produces deterministic per-lane results and dispatch order. This is event-time fairness, not CPU preemption, wall-clock latency or equal throughput; trusted synchronous providers can still block.

Workflow dispatch privately stages one candidate workflow and temporal book, then commits them and removes that lane's head together. Its Workflow outcome includes the original immutable as-of alignment snapshot; later queued/publication state cannot replace it. It exposes only data available at that source phase, not a simultaneous cross-domain graph join. A failed lane returns a Rejected outcome, becomes Blocked and retains its unchanged head and all committed computation state. Other lanes can progress. `retry(id)` explicitly reactivates the same head; repeated failure never advances provider/crossing/window history. This control transition/fairness cursor can advance on rejection while financial/strategy state does not.

Blocked lanes do not stall unrelated lane timers/outputs. Consequently, retrying an old blocked lane can produce an older event-time outcome after another lane has progressed. Cross-lane outcome order is not a new global market sequence or exactly-once durable stream; use lane/run/opening/source identities and retain the explicit control-command sequence. Market publication order and each lane's own source order remain fixed. Neither successful enqueue nor a copied Rust object implies external delivery acknowledgement.

## Cancellation and end of input

Lane status is Active, Blocked, Stopped or Completed. `cancel` is allowed only for Active/Blocked, calls workflow stop to release owned provider state, discards that lane's pending deliveries and active windows/timers, reports discarded count/incomplete window values and releases capacity. It is terminal and never emits an expiry decision. Cancellation occurs at synchronous boundaries and does not interrupt a running provider/worker.

`finish` requires Active, all market streams sealed and drained, that lane's FIFO empty and no pending event-time timer. It completes the workflow, returns remaining count windows as incomplete and clears them. Missing future bars never fabricate an expiry at EOF. Blocked lanes must retry or cancel; repeat terminal operations fail. All lanes may share a model while finishing/canceling independently. No hot attach, lane restart/resume, timer permission system or worker disposal is silently supported. New host instances can construct fresh runs; compatible recovery belongs to P2-04.

As in the existing runtime, Result-based rollback excludes allocation/process failure, hostile provider sharing, arbitrary side effects and panics outside the trusted provider boundary. This profile bounds admission/queues/state; it does not enforce OS memory/CPU limits, interruption deadlines or production isolation. Window state/queue/fairness inspection is not a durable snapshot.
